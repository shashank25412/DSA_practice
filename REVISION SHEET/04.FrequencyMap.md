# Stage 3A — Frequency Map Pattern (HashMap Thinking)

## Why this comes after Sliding Window
Sliding Window taught:

`expand → shrink → evaluate`

Mental shift:
> Don’t recompute what can be remembered.

HashMap generalizes this:

> **What information from the past should I remember so I never search again?**

Sliding Window stores:
- current window state

HashMap stores:
- past computation / lookup memory

---

## Core Mental Shift

Brute force:
- repeated searching
- repeated counting
- nested loops

HashMap:
- remember once
- O(1) lookup
- reuse forever

Invariant:

> **What information about the past am I storing?**

---

# Universal HashMap Flow

Equivalent of Sliding Window:

`LOOKUP → UPDATE → EVALUATE`

Compressed framework:

1. What repeated work exists?
2. What past information should I store?
3. Lookup first or update first?

## Step 4 — Lookup First vs Update First

### A) Lookup → Update

Used in:
- pair lookup
- complement
- existence matching

Example:
### LC 1 — Two Sum

Rule:
> current element checks against the past

Template:

```cpp
for(element){

    lookup();

    update();
}
```

Why?
To avoid self-pairing.

---

### B) Update → Evaluate

Used in:
- frequency problems
- counting
- occurrence tracking

Example:
### LC 242 — Valid Anagram

Template:

```cpp
for(element){

    update();

    evaluate();
}
```

Rule:
> counting problems usually update first

# 4 Master Templates

## 1. Existence Template

Use when:
- seen before?
- duplicate?
- exists?

```cpp
unordered_set<int> seen;

for(auto x : nums){

    if(seen.count(x)){
        // found
    }

    seen.insert(x);
}
```

Stores:
`value -> existence`

Problems:
- LC 217
- LC 202
- LC 128

---

## 2. Frequency Template

Use when:
- count
- frequency
- occurrence

```cpp
unordered_map<int,int> freq;

for(auto x : nums){
    freq[x]++;
}
```

Stores:
`value -> count`

Problems:
- LC 242
- LC 347
- LC 169

---

## 3. Index Tracking Template

Use when:
- pair lookup
- complement
- index retrieval

```cpp
unordered_map<int,int> seen;

for(int i=0; i<nums.size(); i++){

    int need = target - nums[i];

    if(seen.count(need)){
        return {seen[need], i};
    }

    seen[nums[i]] = i;
}
```

Stores:
`value -> index`

Problems:
- LC 1
- pair problems

Invariant:
> map contains everything before i

---

## 4. Grouping Template

Use when:
- group similar items
- bucket
- classify

```cpp
unordered_map<string, vector<string>> groups;

for(string s : strs){

    string key = createKey(s);

    groups[key].push_back(s);
}
```

Stores:
`signature -> group`

Problems:
- LC 49

# Two Sum Intuition

Repeated work:
> searching complement repeatedly

Brute force:
O(n²)

HashMap:
O(n)

Stored state:
```cpp
number -> index
```

Why lookup first?

Wrong:
```cpp
insert
lookup
```

May self-pair.

Correct:
```cpp
lookup
update
evaluate
```

Master code:

```cpp
vector<int> twoSum(vector<int>& nums, int target) {

    unordered_map<int, int> seen;

    for (int i = 0; i < nums.size(); i++) {

        int need = target - nums[i];

        if (seen.count(need)) {
            return {seen[need], i};
        }

        seen[nums[i]] = i;
    }

    return {};
}
```

Invariant:
> hashmap contains all elements before current index

# LC 387 — First Unique Character

Canonical solution:
### 2-pass O(n)

Why?

Need:
> global uniqueness

Current character depends on future.

Example:
`leetcode`

At index i:
You don't yet know whether character appears later.

Solution:

Pass 1:
```cpp
count frequency
```

Pass 2:
```cpp
find first count == 1
```

Still:
`O(n)`

Because:
`O(n) + O(n) = O(n)`

---

## Can it be done in one pass?

Yes, but more complex.

Idea:
- frequency map
- ordered structure

Example:
`LinkedHashMap` in Java

Concept:
- first occurrence → candidate unique
- second occurrence → remove candidate

But interview preference:

Prefer:
```text
simple O(n)
```

over:
```text
clever O(n)
```

unless explicitly asked.
